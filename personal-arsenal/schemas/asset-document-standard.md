# 资产文档规范

所有 Topic 的长期维护型 Markdown 资产都使用以下共享结构。它是可复用的骨架，不要求每个章节都必须填满。可根据资产类型调整细节；确实不适用的章节标记为 `N/A`，未知事实明确注明未知。不要为了填满模板而编造内容。

## 1. 资产元数据

- **资产 ID：**
- **标题：**
- **Topic：**
- **资产类型：**
- **状态：** draft / active / deprecated / archived
- **创建日期：**
- **更新日期：**
- **关联资产：**

## 2. 概述

该资产解决什么问题？为什么值得保留？

## 3. 背景 / 上下文

相关项目背景、技术环境和使用场景。

## 4. 问题 / 目标

该资产要解决的具体问题或达成的目标。

## 5. 设计 / 技术细节

架构、实现方式、技术原理和关键设计决策。

## 6. 流程 / 操作步骤

实际操作步骤、工作流或使用方法。

## 7. 验证 / 证据

验证方式、结果和证据来源。区分观察事实、推断和未确认假设。纳入前先对证据脱敏。

## 8. 经验总结

工程经验、重要判断、失败路径和注意事项。

## 9. 复用指南

适合复用的场景及复用前提。

## 10. 局限 / 未决问题

已知限制、尚未验证的问题和后续工作。

## 11. 参考资料

关联文件、代码、外部资料和其他资产。

## 故障排查案例补充要求

故障排查类资产还必须记录：

- **时间线：**按日期记录观察和操作。
- **证据：**证据来源及准确观察结果，并完成安全脱敏。
- **假设：**每项假设，以及支持或反驳它的证据。
- **根因：**已确认的原因；若未确认，应明确标记为未解决。
- **修复：**实际修改内容、作用范围和理由；不得暗示尚未实施的建议已经生效。
- **验收：**执行过的检查及其结果，包括未验证的项目。

不得包含真实 API Key、Webhook URL、Secret、代理凭据、含凭据日志、未脱敏截图、`.env` 文件或个人 / 系统敏感信息。
