# Workbench 总体架构

## 定位

Personal AI Workbench 是由多个独立产品组成的个人 AI 工作台。Workbench 负责提供统一入口、共享基础设施和跨产品协作能力。当前三个核心产品为 Project Replay、Personal Arsenal 和 Personal Knowledge，三者平级并拥有独立业务边界。

## 目录职责

### `apps/`

客户端入口，包括 Web 和 Android。客户端负责面向用户提供 Workbench 入口，不等同于产品业务模块；产品业务边界由 `products/` 表达。

### `products/`

承载各个独立产品的业务边界、产品文档与演进空间。产品定义文档位于对应产品目录的 `README.md`：

- `project-replay/`：历史项目重演与工程经验复现。
- `personal-arsenal/`：个人工程武器库，沉淀可复用工程能力。
- `personal-knowledge/`：个人技术知识库，沉淀和检索认知资产。

三个产品是平级关系，不将其中任何一个作为另一个产品的子模块。

### `services/`

承载可被多个产品共享的后端能力。共享服务不应成为所有产品业务逻辑的集中容器；各产品仍保持清晰的业务归属。

### `docs/`

存放 Workbench 整体架构、跨产品架构说明和重要架构决策。产品自身的定位、目标、边界和能力范围归属各自的 `products/*/README.md`。

## 产品关系

- **Project Replay**：复现和验证工程经验。
- **Personal Arsenal**：沉淀和复用工程能力。
- **Personal Knowledge**：沉淀和检索认知资产。

三者可通过明确接口和共享能力协作，但当前不规定具体调用关系或流程。协作方式应在需求明确后再定义。

## 共享基础设施

Workbench 的共享基础设施用于支撑多个产品的运行和协作，并提供统一入口。共享能力应有明确边界和接口；具体能力范围依据实际需求逐步确定，不能因此模糊产品业务归属。

## 架构原则

1. 三个产品业务平级，各自拥有独立业务边界和演进空间。
2. Workbench 提供统一入口、基础设施和跨产品协作能力。
3. `apps` 是客户端入口，不等同于产品业务模块。
4. `products` 表达业务产品边界。
5. `services` 提供共享后端能力，不承载所有产品的业务逻辑。
6. 产品之间通过明确接口和共享能力协作，避免隐式耦合；不预设尚未确定的调用流程。
7. 当前采用 Monorepo 不代表未来必须采用微服务。
8. 先建立清晰模块边界，再根据真实需求决定是否拆分服务。
9. 当前架构状态为 **Active Baseline**，允许通过 **Audit → Decision → Card → Construction** 持续演进。

## 当前状态

本架构说明定义当前基线和边界，不代表所有实现方案已经确定。产品范围、共享能力和协作方式可在后续审视与决策中演进。
